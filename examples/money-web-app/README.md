# End-to-end Example: PocketLedger — a Money-Tracking Web App with Auth

> A security-heavy example walking the FULL chain — portfolio scorecard → discovery → the six lifecycle stages — for a basic personal money-management web application (registration/login + income/expense tracking + monthly summary). Where [`mini-todo-api`](../mini-todo-api/) shows a "first run", this one shows what changes when the product touches **authentication and financial data**: threat modeling, SR-x security requirements, security gates, and UX gates all fire.

**Product:** PocketLedger — web app, server-rendered (Node 22 · Express · SQLite · htmx). No payment processing — it tracks money, it doesn't move it.
**Team:** Lan (owner), Minh (Spec Reviewer + release manager), builder-claude at **L1** (autonomy policy active). Walk stage of adoption (`docs/en/07-adoption.md`).

## Stage −1 · PORTFOLIO — is this worth discovering?

The scorecard scored **108/729** (alignment 3 × demand 3 × force 1 × readiness 3 × delay 2 × confidence 2) → above the team threshold of 100 → discovery funded. No dimension was zero → no veto. Full reasoning: [`priority-scorecard.md`](priority-scorecard.md).

## Stage 0 · DISCOVERY — evidence before intent

- **Demand mining (AI-assisted):** agents clustered 9 months of internal-support tickets: 214 requests for "expense tracking that isn't the shared spreadsheet"; the spreadsheet had been corrupted twice (`docs/en/09-discovery-ux.md` §2).
- **Stakeholder map:** users = employees themselves; decision = Ops lead; blockers = Security (financial data!) — Security Lead consulted from day one.
- **Feasibility screen:** technical ✅ (plain web stack, spikes not needed); economic ✅ (estimate 4–6 medium tasks); regulatory ✅ (internal tool, but financial data → **restricted** classification → threat model mandatory).
- **UX:** 3 wireframe directions generated by the agent from user stories; 5-user usability test on the clickable prototype → "add transaction" flow simplified to 2 fields before any backend existed. **Usability-Ready: passed.**
- **Decision logged:** ADR-0007 "Server-rendered + htmx over SPA" (context: one squad, L1 agents, SSR easier to verify for agents than client state).

## Stage 1 · PLAN — intent with a security screen that lights up

Lan writes [`intent.md`](intent.md). The **security screen** (new in the template) flags: auth ✅, money data ✅, PII ✅ (restricted classification), trust boundary ✅ → threat model REQUIRED at Design. Intent-Ready gate passes: evidence (ticket clustering + spreadsheet incidents), metric (weekly tracked expenses logged by ≥ 60% of users within 6 weeks), non-goals (no payment processing, no mobile app, no multi-currency).

## Stage 2 · DESIGN — spec + threat model in one session

One agent session (high-reasoning model, temp 0.2) produces [`spec.md`](spec.md) + [`threat-model.md`](threat-model.md):

- 3 functional requirements with measurable acceptance criteria
- **6 security requirements SR-1…SR-6** derived from the threat model — argon2id password hashing, HttpOnly/Secure/SameSite sessions with expiry, per-user data scoping (authz matrix test), log masking of amounts, login rate-limiting, WCAG 2.2 AA
- Task breakdown: **T1 auth module — complexity 7 → ai-assisted** (sensitive path; human leads, agent drafts), **T2 transactions CRUD — 4 → ai-with-review**, **T3 summary dashboard — 4 → ai-with-review**, **T4 user guide — 2 → ai-with-review**
- Threat model: 3 trust boundaries, 6 STRIDE rows, agentic threats checked (prompt injection via category names, sandbox egress, dependency poisoning)

**DoR:** Minh catches two gaps — SR-3 lacked the cross-user test matrix (user A must not read user B's ledger), and T3 lacked the "> 10k transactions" boundary. Fixed → **dispatch allowed.**

## Stage 3 · BUILD — the sensitive task routes differently

- **T1 (auth, complexity 7) runs ai-assisted:** Minh leads; builder-claude drafts the session module and the SR-1/SR-2 tests; CODEOWNERS adds `src/auth/**` → Security Lead is a required reviewer. The agent twice proposed `localStorage` for session tokens — AGENTS.md security rules made it flag the conflict and ask instead of guessing. PR #201: 190 lines (within L1 ≤ 200).
- **T2 (transactions CRUD) runs ai-with-review:** full plan in [`plan.md`](plan.md) — files, tests (including the ownership matrix), rollback. Plan approved in 2 minutes; code delivered on iteration 2.
- Secret-scan fires once during T1: a test fixture contained a realistic-looking API key pattern → replaced with an obvious fake. **The hard gate worked.**

## Stage 4 · TEST — security gates earn their keep

- Cross-harness review: the GPT reviewer catches a missing `401` on expired sessions (4/5); the Gemini reviewer independently flags the same path (3/5) — builder fixes, re-run 5/5.
- **Security evals** (new type): "agent must scope queries by session owner" passes; "no amounts in logs" catches one `console.log(amount)` → fixed.
- **DAST against staging finds the login endpoint had no rate limiting** (SR-5 was specced but the implementation missed it) → soft-mandatory gate `security-dast-critical` blocks the release candidate. Agent adds the limiter + tests + a regression eval. This is exactly the failure mode the 45%-flawed-AI-code stat predicts — the gate battery exists for it.
- Coverage diff 88%; SBOM generated; docs-ship gate: the user guide (T4) merged with the feature PRs, not after.

## Stage 5 · DEPLOY — hard gates hold

Production deploy held by hook for Minh (release-manager role). Checklist before approval: DAST re-scan green, rollback runbook (feature flag `pocketledger.enabled`, DB migration is additive), canary 5% → 25% → 100% over 3 days. Audit trail records approver + reports used.

## Stage 6 · MAINTAIN — the loop, security-flavored

- Week 2: the SRE agent's brute-force detector sees repeated failed logins from one IP → opens a security investigation (not a code bug). Findings: rate limiter works; recommendation → add exponential backoff → **new intent `INT-202612-002`** (born from Maintain, tagged `security`).
- Week 4: "this page didn't help" signal on the import guide → docs-feedback intent.
- Metrics snapshot: `task.success_rate` 4/4 · acceptance_rate 0.5 after iteration-2 (above the 0.27–0.30 baseline) · intervention 2/4 tasks (the sensitive ones, by routing design) · cost/task $3.40 · security evals 100% · DAST findings-to-production: **0 escaped**.

## Lessons this example exists to teach

0. **It runs, and the requirements are verified against behavior, not narrative** — see [`app/RUN-REPORT.md`](app/RUN-REPORT.md): 22/22 gate tests green, and the run itself caught three real defects (argon2 output format, a silent no-op in edit, an auth-coverage check bug). The layered-verification claim of the framework is demonstrated, not asserted.
1. **The security screen → threat model → SR-x → gate chain is one continuous line** — a "yes" in the intent automatically becomes tests and gates three stages later. Nothing relies on someone remembering to "think about security".
2. **Routing protects the sensitive parts:** the auth module never went autonomous — complexity 7 forced ai-assisted with the Security Lead on CODEOWNERS.
3. **Gates caught what review missed** (rate limiting) — layered controls, not hero reviewers.
4. **The agent escalated instead of guessing** when spec and habits conflicted — because AGENTS.md security rules told it to. Context engineering IS security engineering.
